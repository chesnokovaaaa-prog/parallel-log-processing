## Аналитические выводы

### 1. Влияние GIL на многопоточность (Threading)
Парсинг логов — это чисто вычислительная нагрузка (**CPU-bound**). Из-за **GIL (Global Interpreter Lock)** в CPython потоки не могут выполняться параллельно на разных ядрах процессора. Они непрерывно конкурируют за замок GIL. На файле 5M строк многопоточная версия показала худший результат (**51.84 сек**), что почти в 3 раза медленнее обычного однопоточного Baseline.

### 2. Оценка эффективности Multiprocessing и закона Амдала
Использование `ProcessPoolExecutor` позволило обойти GIL, так как каждый процесс получил свой независимый интерпретатор. На больших данных время сократилось до **6.65 сек**. Эмпирическое ускорение составило $S = 2.75$. Отсюда доля строго последовательного кода (инициализация через `spawn` на macOS, финальный merge тяжелых структур для p95) составляет $s \approx 27\%$.

### 3. Аномалия производительности Pandas
Пакетное чтение через Pandas (`chunksize=200k`) на 5M строк показало неожиданное падение скорости до **47.39 сек**. Это связано с использованием регулярного выражения в параметре разделителя (`sep=r'\s+'`), что заставило Pandas переключить внутренний движок со сверхбыстрого Си на медленный Python-парсер строк. 

### 4. Преимущество архитектуры Pipeline (Producer-Consumer)
Вариант D показал абсолютный рекорд скорости (**6.28 сек**). Выделение ввода-вывода (I/O) в отдельный поток с немедленной диспетчеризацией текстовых чанков по процессам-вычислителям обеспечило идеальное перекрытие фаз работы. Платой за скорость стал высокий пик памяти (**1392.49 МБ**).
